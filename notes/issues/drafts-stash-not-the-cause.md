root cause of the "No stashed content found" 412 in the 2017 wikitext editor: MediaWiki's Parsoid render stash expires, not the Drafts extension; fix is two `LocalSettings.php` lines.

## affected versions

| component | version |
|---|---|
| MediaWiki | 1.44 (REL1_44) |
| Drafts | 0.3.8 (REL1_44; `github.com/wikimedia/mediawiki-extensions-Drafts` @ `4a04b28`) |

## symptom

when a user keeps an edit session open in the 2017 wikitext editor (new wikitext editor / NWE, which VisualEditor provides) and tries to save after roughly a day, the save panel shows:

> No stashed content found for `<revisionID>/<UUID>`. This is most likely because your edit session has expired. Try to copy your changes, reload the page, and try again.

the Drafts extension is **not the cause**. this error originates in MediaWiki core's Parsoid render stash, which the REST `transform` endpoint consults when NWE/VE submits its HTML for selser-based serialization.

## where the error comes from

- message id: `rest-no-stashed-content` ([`includes/Rest/i18n/en.json:77`](../../devel/MediaWiki/includes/Rest/i18n/en.json#L77))
- thrown at: [`HtmlInputTransformHelper::setOriginal`](../../devel/MediaWiki/includes/Rest/Handler/Helper/HtmlInputTransformHelper.php#L494); a 412 fires when `fetchSelserContextFromStash()` returns null
- stash key shape: `<revisionID>/<UUID>`, built by [`ParsoidRenderID`](../../devel/MediaWiki/includes/edit/ParsoidRenderID.php#L29). the UUID is a v1 UUID generated by `GlobalIdGenerator->newUUIDv1()` in [`ParserCache.php:545`](../../devel/MediaWiki/includes/parser/ParserCache.php#L545) and [`RevisionOutputCache.php:299`](../../devel/MediaWiki/includes/parser/RevisionOutputCache.php#L299)
- stash backing store: [`SimpleParsoidOutputStash`](../../devel/MediaWiki/includes/edit/SimpleParsoidOutputStash.php), backed by a `BagOStuff` chosen by `$wgParsoidCacheConfig['StashType']`

## why Drafts is not involved

`devel/Drafts/extension.json` only registers hooks for the classic `EditPage` flow:

| hook | purpose |
|---|---|
| `EditPage::showEditForm:initial` | loads draft into `$editpage->textbox1` |
| `EditPage::attemptSave:after` | no-JS fallback for the Save Draft button |
| `EditFilter`, `EditPageBeforeEditButtons`, `PageSaveComplete`, etc. | classic-editor side effects |

the client-side `modules/ext.Drafts.js` only attaches to `document.editform` and `form.wpTextbox1`. NWE and VE render their own UIs and never instantiate `EditPage`'s form, so none of Drafts' hooks fire and the JS module never finds an editform to bind to. with NWE enabled by default for this wiki (`$wgDefaultUserOptions['visualeditor-newwikitext'] = 1` in `config/LocalSettings.php:197`), Drafts is essentially inert for the editor that produces this error.

the error reproduces with Drafts disabled.

## why the UUIDs look non-unique but aren't

two examples from the screenshots:

```
28642/39e52c40-50ce-11f1-a791-a705bb288163
28489/c5ccac41-48b5-11f1-a791-a705bb288163
```

both UUIDs end in `-11f1-a791-a705bb288163`. that is not a uniqueness bug; it is the structure of a UUID v1:

| segment | bytes | meaning |
|---|---|---|
| `39e52c40` | 4 | `time_low` (changes every ~100 ns) |
| `50ce` | 2 | `time_mid` |
| `11f1` | 2 | `time_hi_and_version` (`1` = UUID v1) |
| `a791` | 2 | `clock_seq` (per-process, stable) |
| `a705bb288163` | 6 | node id (per-host, stable) |

`clock_seq` and node id are stable for the lifetime of a process / host, so every v1 UUID generated by the same wiki instance shares that 8-byte suffix. the uniqueness is carried by the time fields, and those *do* differ between the two examples (`39e52c40-50ce` vs `c5ccac41-48b5`). the full keys also differ in their revision-id prefix (`28642` vs `28489`).

## why the stash expires

`$wgParsoidCacheConfig` is not overridden in [`config/LocalSettings.php`](../../config/LocalSettings.php), so it uses the schema defaults in [`MainConfigSchema.php:4173`](../../devel/MediaWiki/includes/MainConfigSchema.php#L4173):

```php
'StashType' => null,            // falls back to MainStash
'StashDuration' => 24 * 60 * 60, // 1 day
```

`$wgMainStash` is also unset, so it falls back to its own schema default `CACHE_DB` (`MainConfigSchema.php:4145`). net effect: the Parsoid render stash lands in the SQL `objectcache` table with a 24-hour TTL, even though Redis is already configured and used for `$wgMainCacheType`, `$wgSessionCacheType`, and `$wgParserCacheType`.

a user who opens NWE on Monday and clicks Save on Tuesday will hit a 412. the Drafts extension persists *wikitext* for 30 days (`$egDraftsLifeSpan`), which makes the gap visible: the user thinks the draft is safe and comes back later, but NWE has long since lost its render context.

## fix

two independent changes, both in `config/LocalSettings.php`:

1. use Redis for the Parsoid stash so it survives `objectcache` table purges and is not fighting MariaDB for storage:

   ```php
   $wgParsoidCacheConfig['StashType'] = CACHE_REDIS;
   ```

1. lengthen the TTL so long edit sessions do not silently rot. 7 days is a reasonable compromise between recovery window and memory pressure:

   ```php
   $wgParsoidCacheConfig['StashDuration'] = 7 * 24 * 60 * 60;
   ```

optionally also set `$wgMainStash = CACHE_REDIS;` so other stash-like data (edit stash, login throttles, etc.) gets the same treatment; separate decision, but worth considering since Redis is already running.

## what this does not fix

- NWE/VE has no UI to "re-stash" a missing original render and recover gracefully; even with the fix above, a long-enough gap still produces the same error, just less often. upstream issue, not local
- Drafts does not capture the Parsoid render context, so restoring a draft into NWE does not repopulate the stash. out of scope here
